## 角色与唯一写入

- 总控：冻结功能目标、业务/架构合同及权限；验收完整候选；唯一写 Brain 和项目治理记录。
- **PageNest 代码管理**：独立可见对话框，唯一 Git writer，负责基线、功能分支、提交/推送、PR、准确 SHA 合入、远端读回与迭代记录。业务改动需实现角色交付及总控 ACCEPT；不自己扩大功能或重写业务代码。
- **PageNest V1 实现**：唯一业务 writer，在总控/代码管理已分配的功能分支连续实现和必要自检；不切其他分支、不自行 commit/push/merge。未来按具体功能安排 writer，不让两个 writer 重叠修改。
- 执行对话框为用户指定 GPT-6.1 Sol / High / Fast；实际值按 fresh session 核实，unknown 如实保留。测试规模仍按最小充分原则。

## 分支

`main` 仅保留已验收、可说明可用范围的基线。首个 README 初始化是仓库种子，不包含业务代码。禁止将未验收变更直接提交或推送 main。

| 类型 | 命名与示例 | 粒度 |
|---|---|---|
| 仓库/协作设置 | `chore/repository-setup` | 本轮治理与 PR 基础 |
| 用户审核原型 | `design/html-prototype` | 单文件模拟三页和交互，用户审核门禁 |
| 首版完整流程 | `feat/local-reading-library` | 导入、分类、隔离阅读、原文及持久化共同构成可独立验收的首版；一个连续 writer |
| 后续独立模块 | `feat/html-import`、`feat/folder-management`、`feat/source-reader` | 仅当该功能确有独立需求/输入输出/验收时创建；不提前创建空分支 |
| 缺陷 | `fix/reading-position` | 一个具体缺陷和必要邻接修改 |
| 文档 | `docs/reading-guide` | 一个文档目的 |

相关模块属于同一不可分的用户流程时放一个功能分支，不为 helper、单文件或适配模型切碎同一功能。模块可以并行，前提是没有共享写入与未冻结依赖；必要时另建独立 worktree，不能多人切同一 checkout。

## 一次迭代

1. 总控冻结一个可观察功能和 allowlist；代码管理核对工作区、origin/main、base/HEAD，保留所有已有改动，再分配分支。
2. 实现角色连续完成该功能及轻量自检，交完整候选与同源码状态证据。
3. 总控做一次产品/架构 ACCEPT / REJECT；独立只读复审仅在实际风险需要时介入，不为每次小修改重复测试。
4. 代码管理检查最终 diff、逐项 staged 文件、秘密/个人运行数据排除；提交到对应功能分支并 push，核对远端 SHA；创建或更新一个 PR，挂到代码管理对话框。
5. PR 描述写问题、结果、验证及限制。无相关新风险不重跑相同测试；纯规则只内容/diff/config 解析。不得为了规范化立即增加庞大 CI 或强制不存在的 checks。
6. 代码管理只有在总控明确 ACCEPT 且 PR head 与已验收 SHA 一致后，按授权 squash merge 到 main；从远端读回合并 SHA与状态，更新基线。若新增 commit、冲突或 CI 真失败，回到受影响范围修正/验证。
7. 更新 Brain devlog → index → 日志由总控负责。不要自动删未合并或有独有提交/dirty 的分支与 worktree；不 reset/clean/stash 清场，不 force push。

用户已授权本项目按上述规范进行正常分支提交、PR 与逐步合并；这不授权公开仓库、付费、凭据操作、部署、用户资料上传或跨项目外部写入。代码管理不能自行把未验收业务候选合入 main。

## main 保护

本地设置 `git config core.hooksPath .githooks`，pre-push 禁止直接推送 main。该 hook 是本机辅助，不代表 GitHub 服务端已保护；新 checkout 需重新配置。

代码管理尝试为 main 设置最小服务端 PR 门禁、禁止 force push/删除；不强制自己无法完成的他人审查或不存在的 CI。若当前 GitHub 私有仓库计划不支持保护，记录 API 的准确限制，保留本地 guard 与对话框约定；不升级收费套餐、不伪报已保护。
